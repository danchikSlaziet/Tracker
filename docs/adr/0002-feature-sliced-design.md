# 2. Выбор архитектурного подхода Feature-Sliced Design (FSD)

* Статус: Принято
* Дата: 2026-07-02

## Контекст и проблематика
Стандартная структура фронтенда с разделением по типам файлов (`components/`, `hooks/`, `services/`) быстро деградирует по мере роста приложения. Возникает сцепленность компонентов (spaghetti code), циклические импорты и размытие зон ответственности между бизнес-логикой и UI.

## Принятое решение
Использовать методологию **Feature-Sliced Design (FSD)** для структурирования `apps/frontend`.
Слои приложения распределены с жестким правилом однонаправленного потока импортов (нижние слои не имеют права импортировать из верхних):
- `shared/` — Переиспользуемая инфраструктура (API клиент, хелперы, базовый UI).
- `entities/` — Бизнес-модели данных (Transaction, Category, User).
- `features/` — Пользовательские сценарии (Auth, CreateTransaction, ImportBankStatement).
- `widgets/` — Композиция фичей и сущностей в крупные самостоятельные блоки UI.
- `pages/` — Страницы приложения.
- `app/` — Инициализация, стили, провайдеры контекста и роутинг.

Каждый слайс обязан предоставлять строго ограниченный Публичный API (`index.ts`). Обход публичных API запрещён и контролируется FSD-линтером **Steiger**.

## Альтернативы
1. **Classic Layered Architecture (`components/`, `pages/`, `services/`)**: Быстрая на старте, но приводит к высокому техническому долгу при масштабировании.
2. **Modular Architecture (by Domain)**: Домены часто переплетаются и вызывают циклические зависимости без четких слоев абстракции FSD.

## Последствия
### Плюсы
- Высокая изолированность кода и простота рефакторинга.
- Четкие правила импортов исключают циклические зависимости.
- Масштабируемая структура, готовая к продуктовой разработке.

### Минусы
- Необходимость написания явных Публичных API (`index.ts`) для слайсов.
- Порог вхождения при знакомстве с новыми слоями.
