# 6. Стратегия тестирования: Vitest, React Testing Library и Playwright

* Статус: Принято
* Дата: 2026-07-20

## Контекст и проблематика
Для обеспечения стабильности приложения при рефакторинге и добавлении новых фич необходимо автоматическое покрытие тестами на разных уровнях пирамиды тестирования. 

## Принятое решение
Сформировать трехслойную стратегию тестирования:

1. **Unit & Integration Tests (Vitest + React Testing Library)**:
   - Покрытие изоляции бизнес-логики (хелперы, утилиты типа `formatMoney`, `useDebounce`).
   - Интеграционное тестирование UI-компонентов и виджетов (`LoginForm`, `CategoryForm`, `CategoriesWidget`, `DashboardWidget`) с мокированием API-запросов.
   - Быстрый запуск в рамках единого окружения Vite.

2. **End-to-End Tests (Playwright)**:
   - Проверка критических сценариев пользователя от начала до конца (Регистрация + OTP код, Авторизация, Добавление/Удаление транзакции, Добавление/Удаление категории).
   - Тестирование в реальных браузерах (Chromium, Firefox, WebKit, Mobile Safari, Mobile Chrome).
   - Использование паттерна **Page Object Model (POM)** для чистой структуры тестового кода (`LoginPage`, `TransactionsPage`, `CategoriesPage`).

3. **FSD Linter (Steiger)**:
   - Проверка корректности архитектуры и отсутствия несанкционированных импортов в обход Публичных API.

## Альтернативы
1. **Cypress для E2E**: Занимает больше времени при запуске и тяжелее интегрируется в мультиварантные профили устройств по сравнению с Playwright.
2. **Jest вместо Vitest**: Jest требует отдельной сложной настройки трансформаторов для проекта на Vite, в то время как Vitest работает из коробки с той же конфигурацией плагинов.

## Последствия
### Плюсы
- Высокая уверенность при рефакторинге ключевой логики.
- Полное соответствие стандартам разработки в коммерческих продуктах.

### Минусы
- Затраты времени на поддержку Page Object моделей и моков при изменении интерфейса.
