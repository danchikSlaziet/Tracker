# 4. Монорепозиторий и совместное использование типов (shared-types)

* Статус: Принято
* Дата: 2026-07-08

## Контекст и проблематика
При раздельном ведении фронтенд и бэкенд репозиториев неизбежно возникают рассинхронизации контрактов API (DTO, интерфейсы моделей). Изменение поля в бэкенд-модели не подсвечивается компилятором TypeScript на фронтенде, что приводит к runtime-ошибкам на продакшене.

## Принятое решение
Использовать структуру **монорепозитория** на базе встроенного механизма **npm workspaces**.
Выделить пакет `packages/shared-types`, который содержит:
- Общие модели данных (`Transaction`, `Category`, `User`).
- Data Transfer Objects (`CreateTransactionDto`, `LoginDto`, `VerifyOtpDto`).
- Общие енумы и юнион-типы.

Бэкенд и фронтенд импортируют типы напрямую из `@finance/shared-types`. При изменении типа в `shared-types` компилятор мгновенно подсвечивает несовместимость в обоих приложениях.

Также выделен пакет `packages/ui-kit` (Storybook) для изоляции и тестирования базовых компонентов UI (кнопки, инпуты, модальные окна).

## Альтернативы
1. **Дублирование типов на фронтенде и бэкенде**: Вызывает рассинхрон при рефакторинге.
2. **Отдельный npm-пакет типов в приватном registry**: Избыточная сложность публикации и задержка обновления зависимостей при локальной разработке.

## Последствия
### Плюсы
- Единая точка правды для всех бизнес-контрактов.
- Ошибки несоответствия типов обнаруживаются на этапе сборки (`npm run build`).
- Удобство атомарных коммитов, затрагивающих и клиент, и сервер.

### Минусы
- Требуется корректная настройка TypeScript `references` или сборки локальных пакетов.
